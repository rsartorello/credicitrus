CMS Credicitrus — Banco de Dados e Integração

Orientação operacional para provisionamento do SQL Server, execução dos scripts e devolutiva dos dados necessários à integração com a aplicação Next.js.
Versão: 1.2 · Data: 24/09/2026 · Ambiente alvo: Dev e/ou Produção (isolados)

1. Objetivo

Preparar um banco SQL Server dedicado ao CMS do novo site Credicitrus, com schema, categorias iniciais e usuário administrador, e devolver à equipe de desenvolvimento os parâmetros de conexão e infraestrutura para integração no projeto.

2. Pré-requisitos (lado TI)

  • Instância Microsoft SQL Server acessível pela aplicação (rede/firewall liberados).
  • Permissão para criar database e login (ou database já criada + usuário com DML/DDL necessários).
  • Pasta de uploads fora do diretório sobrescrito no deploy, com escrita para a conta do processo Node.
  • Scripts SQL entregues pela equipe de desenvolvimento na pasta sql/ do repositório.

4. Procedimento — criação do banco e scripts

  1. Criar o database (um por ambiente), por exemplo: 
    CREATE DATABASE CredicitrusCms;
GO
USE CredicitrusCms;
GO
    Em produção, usar nome acordado e registrar em DATABASE_NAME.
  2. Criar login/usuário SQL com senha forte, permissões no database (SELECT/INSERT/UPDATE/DELETE nas tabelas do CMS; evitar sa em aplicação).
  3. Executar os scripts nesta ordem exata (SSMS, Azure Data Studio ou sqlcmd), conectado ao database criado:
    1. 001_schema.sql — tabelas de conteúdo + audit
    2. 002_seed_categories.sql — categorias iniciais
    3. 003_users.sql — usuários e permissões
    4. 004_session_version.sql — SessionVersion
    5. 006_must_change_password.sql — MustChangePassword
    6. 005_seed_admin_suave.sql — usuário inicial super-admin (troca obrigatória no 1º acesso)
    Os scripts são idempotentes (podem ser reexecutados com segurança).
  4. Validar com consultas rápidas: 
    SELECT name FROM sys.tables ORDER BY name;
SELECT Username, DisplayName, IsSuperAdmin, IsActive FROM dbo.CmsUser;
SELECT Module, Slug, Title FROM dbo.DocumentCategory ORDER BY Module, SortOrder;
  5. Criar pastas de upload (fora do path de deploy): 
    {CMS_UPLOAD_PATH}/
  relatorios/
  normativos/
  etica/
  tarifas/
  assembleia/
  banners/
    Exemplos Windows: D:\dados\credicitrus\prod\uploads
    Exemplos Linux: /var/dados/credicitrus/uploads
  6. Testar conectividade a partir do servidor da aplicação (host, porta 1433 ou a configurada, TLS conforme política).

O CMS autentica por Username (não há coluna de e-mail). O endereço acima foi cadastrado como login.

Obrigatório: no primeiro login o CMS redireciona para /admin/trocar-senha e bloqueia o painel até a nova senha ser definida. Não reutilizar a senha inicial como senha definitiva de produção.
Produção: o login bootstrap via variáveis ADMIN_USERNAME / ADMIN_PASSWORD do .env está desabilitado. Use somente usuários da tabela CmsUser.

6. Variáveis de ambiente — formato e devolutiva

Obrigatório: se a TI preencher as variáveis no Azure DevOps, no servidor ou em qualquer painel de configuração, os mesmos valores preenchidos devem ser enviados depois à equipe de desenvolvimento (canal seguro), para atualização / validação no projeto e alinhamento do deploy. Não basta configurar “lá”: sem a devolutiva, o código e o pipeline do time de desenvolvimento ficam desatualizados.

Preferencialmente um bloco por ambiente (Dev e Prod separados). Nunca versionar senhas ou segredos no Git.

6.1 Formato de cada variável

Use exatamente os nomes abaixo. Valores booleanos são literais true ou false (minúsculos, sem aspas). Não use espaços em branco no início/fim do valor.

Variável Obrig. Formato / valores aceitos Exemplo
NODE_ENV Sim Texto fixo: production, development ou test. Em Dev/Prod do servidor use production se o build for de produção. production
NEXT_PUBLIC_SITE_URL Sim URL absoluta pública, com protocolo https://, sem barra final. https://www.credicitrus.com.br
CMS_ENABLED Sim Booleano. Só ativa o CMS se for exatamente true. Qualquer outro valor = CMS desligado (fallback estático). true
DATABASE_HOST Sim Hostname DNS ou endereço IPv4/IPv6 acessível pelo servidor da aplicação. Sem protocolo e sem porta. sql-credicitrus.interno
DATABASE_PORT Sim* Número inteiro (porta TCP). Se omitido, a aplicação assume 1433. 1433
DATABASE_NAME Sim Nome do database SQL Server (identificador; sem espaços preferencialmente). CredicitrusCms
DATABASE_USER Sim Login SQL da aplicação (texto). Não usar sa em produção. credicitrus_cms_app
DATABASE_PASSWORD Sim Senha do login SQL (texto livre; caracteres especiais permitidos). Enviar por canal seguro. (senha forte gerada pela TI)
DATABASE_ENCRYPT Sim* Booleano. TLS na conexão. Se omitido ou diferente de false, a app trata como criptografado (true). true
DATABASE_TRUST_SERVER_CERTIFICATE Sim* Booleano. Só true confia no certificado do servidor (útil em lab/self-signed). Em produção preferir false + certificado válido. false
CMS_UPLOAD_PATH Sim Caminho absoluto no disco do servidor da app, fora do diretório sobrescrito no deploy. Windows: usar barras invertidas ou escapadas conforme o painel; Linux: path POSIX. D:\dados\credicitrus\prod\uploads
/var/dados/credicitrus/uploads
CMS_MEDIA_PUBLIC_PREFIX Não Prefixo de URL pública dos arquivos, começando com /, sem barra final. Padrão se omitido: /media. /media
ADMIN_AUTH_SECRET Sim Segredo opaco, mínimo 32 caracteres aleatórios (hex ou base64). Gerar com openssl rand -hex 32. Único por ambiente; rotacionar no go-live se necessário. a1b2c3… (64 hex)
TRUST_PROXY Cond. Booleano. Use true atrás de reverse proxy (IIS, nginx, Azure) para confiar em X-Forwarded-For. Em local sem proxy: omitir ou false. true
SITE_ROBOTS_INDEX Não Booleano opcional. true = forçar indexação; false = forçar noindex. Se omitido: indexa quando o gate de acesso estiver desligado. true
SITE_ACCESS_ENABLED Não Booleano. Gate temporário /acesso. Manter false em produção pública. Só true ativa o gate. false
SITE_ACCESS_PASSWORD Cond. Texto. Obrigatório apenas se SITE_ACCESS_ENABLED=true. (se gate ativo)
SITE_ACCESS_SECRET Cond. Segredo ≥ 32 caracteres (ex.: openssl rand -hex 32). Obrigatório se o gate estiver ativo. (se gate ativo)
ADMIN_USERNAME / ADMIN_PASSWORD Não (prod) Bootstrap via .env. Em NODE_ENV=production está bloqueado. Não usar em Prod; login só via CmsUser. —

* “Sim*” = fortemente recomendado enviar o valor explícito mesmo quando há padrão na aplicação.

7. Passo a passo — deploy no Azure

A aplicação é Next.js (Node). O pipeline e a infraestrutura ficam a cargo da TI. Não há azure-pipelines.yml no repositório: configure o pipeline no Azure DevOps conforme o padrão interno.

7.1 Ordem recomendada

  1. SQL Server — criar database, usuário e executar scripts 001–006 (seção 4).
  2. Storage de uploads — provisionar pasta persistente (seção 7.2).
  3. App Service (ou equivalente) — criar o app Node por ambiente (Dev / Prod).
  4. Variáveis — preencher App Settings / Variable Group / Key Vault (seção 6).
  5. Pipeline — build e publicação (seção 7.4).
  6. Validação — checklist pós-deploy (seção 7.5).
  7. Devolutiva — enviar bloco 6.3 preenchido à equipe de desenvolvimento.

7.2 Uploads persistentes (obrigatório)

No Azure App Service, o sistema de arquivos do site é efêmero: um novo deploy ou reinício pode apagar arquivos gravados na pasta do app. Os uploads do CMS (CMS_UPLOAD_PATH) não podem ficar nesse disco.
  • Preferir Azure Files montado no App Service (path de mount estável).
  • Apontar CMS_UPLOAD_PATH para o caminho montado (ex.: /home/site/wwwroot-data/uploads ou o path Windows equivalente no mount).
  • Garantir permissão de escrita da identidade do processo Node e backup da share.
  • Criar (ou deixar a app criar) as subpastas: relatorios, normativos, etica, tarifas, assembleia, banners.

7.4 Pipeline Azure DevOps (modelo)

  1. Conectar o repositório Git e apontar o branch de release (ex.: main).
  2. Criar Variable Group por ambiente (ou App Settings no App Service) com as variáveis da seção 6 — secrets em Key Vault / variáveis secretas do pipeline.
  3. Estágio de build (agente Linux ou Windows, conforme padrão TI): 
    npm ci
npm run build
  4. Publicar artefato (pasta do app após build, incluindo .next, package.json, node_modules de produção ou reinstalar no release com npm ci --omit=dev).
  5. Estágio de deploy: publicar no App Service do ambiente alvo e injetar as App Settings (não gravar senhas no YAML do repositório).
  6. Confirmar que o processo sobe com npm start e que as variáveis estão visíveis ao Node em runtime (não só em build, exceto NEXT_PUBLIC_*).
Importante sobre NEXT_PUBLIC_SITE_URL: prefixo NEXT_PUBLIC_ é embutido no bundle no momento do build. Defina o valor correto no pipeline de build de cada ambiente (ou build separado por ambiente).

7.5 Checklist pós-deploy

  • Site público abre (home) sem erro 500
  • /admin/login carrega e autentica com o usuário inicial (seção 5)
  • Upload de PDF de teste em um módulo (ex.: Relatórios) e arquivo aparece em CMS_UPLOAD_PATH
  • URL pública do arquivo via prefixo /media/... responde 200
  • Páginas de Transparência listam o item publicado
  • Após novo deploy, o arquivo de upload ainda existe (prova de storage persistente)
  • SITE_ACCESS_ENABLED=false em produção pública
  • Login em /admin/login → troca obrigatória em /admin/trocar-senha

7.6 Rede e SQL

  • App Service (ou outbound IPs) deve alcançar DATABASE_HOST:DATABASE_PORT.
  • Se SQL for Azure SQL / SQL em VNet: configurar firewall / private endpoint conforme política.
  • DATABASE_ENCRYPT=true em produção; DATABASE_TRUST_SERVER_CERTIFICATE=false com certificado válido.
